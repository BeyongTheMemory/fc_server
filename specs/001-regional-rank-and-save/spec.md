# Feature Specification: 地区排行榜与云端存档(five_card 服务端核心能力)

**Feature Branch**: `001-regional-rank-and-save`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "这个service是/Users/gang.xu/cocos/five_card 的服务端，目前状态是wip，它的预期主要功能包括1. 持久化用户存档，这样切设备了也能用（低优先级）2. 持久化用户最高积分，根据地区生成地区维度的排行榜（高优先级）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传最高分并查看地区排行榜 (Priority: P1)

玩家在 five_card 游戏中打出一局成绩后，成绩被上报到服务端。服务端只保留每个玩家的历史
最高积分，并按玩家所在地区（省、市、区三级）分别维护排行榜。玩家打开排行榜页面时，能
看到自己所在省、市、区三个层级的榜单，了解自己在本地区玩家中的水平。

**Why this priority**: 这是用户明确标注的高优先级功能，也是游戏社交竞争性的核心来源；
没有它，服务端对游戏几乎没有增量价值。

**Independent Test**: 用多个模拟玩家（不同地区、不同分数）上报成绩后拉取榜单，验证各
层级榜单的成员、排序与分数正确，即可独立验证并交付价值，无需存档功能存在。

**Acceptance Scenarios**:

1. **Given** 玩家 A（地区：浙江省/杭州市/西湖区）无历史成绩，**When** A 上报积分 1000，
   **Then** 浙江省榜、杭州市榜、西湖区榜中均出现 A，积分为 1000。
2. **Given** 玩家 A 历史最高分为 1000，**When** A 上报积分 800，**Then** 各榜单中 A 的
   积分仍为 1000，名次不因本次上报下降。
3. **Given** 玩家 A 历史最高分为 1000，**When** A 上报积分 1500，**Then** 各榜单中 A 的
   积分更新为 1500，名次按新积分重新计算。
4. **Given** 同一榜单中玩家 B 与玩家 C 积分相同，**When** 查看榜单，**Then** 先达到该
   积分的玩家排在前面。
5. **Given** 玩家 D 所在区域尚无任何成绩，**When** D 查看榜单，**Then** 返回空榜单而非
   错误，页面可正常展示。
6. **Given** 玩家 A 在西湖区榜排名第 150（超出榜单展示长度），**When** A 查看榜单，
   **Then** A 仍能看到自己的最高分与当前名次。
7. **Given** 玩家 A 上周打出总榜最高分 1500，本周尚未游戏，**When** 进入新的一周后 A
   查看榜单，**Then** 周榜中不含 A（新窗口从零开始），总榜与月榜（若在同月）仍含 A。
8. **Given** 玩家 A 本周已有周榜成绩 500 且历史最高 1500，**When** A 上报 800，**Then**
   总榜不变（800 < 1500），周榜更新为 800（800 > 本窗口 500）。

### User Story 2 - 游戏进度云端存档与恢复 (Priority: P2)

玩家在游戏过程中，进度（如当前关卡、金币等游戏内状态）被自动保存到服务端。玩家关闭游
戏、重装游戏或清除本地数据后再次进入，可以从服务端恢复最近一次保存的进度继续游玩。

**Why this priority**: 用户标注为低优先级，但它是"切设备可用"（User Story 3）的前置能
力；先在同一身份下实现云端保存与恢复，即可独立交付"进度不丢失"的价值。

**Independent Test**: 同一玩家身份保存进度后，模拟"本地数据丢失"（不携带本地进度）再
拉取存档，验证恢复的进度与最后一次保存完全一致。

**Acceptance Scenarios**:

1. **Given** 玩家 A 正在进行一局游戏，**When** 游戏进度发生变化并触发保存，**Then**
   服务端保存的存档更新为最新进度。
2. **Given** 玩家 A 已有云端存档，**When** A 重装游戏后以同一身份进入，**Then** A 可
   恢复到最后一次保存的进度（关卡、金币等状态一致）。
3. **Given** 玩家 A 先后保存两次进度，**When** A 拉取存档，**Then** 恢复的是时间上最新
   的一次（单存档位，新档覆盖旧档）。
4. **Given** 玩家 B 从未保存过进度，**When** B 拉取存档，**Then** 返回"无存档"状态，
   客户端按新玩家流程处理。

### User Story 3 - 跨设备身份识别与存档迁移 (Priority: P3)

玩家更换手机（或在第二台设备上安装游戏）后，通过微信登录证明"我还是我"，随后在新设备
上恢复原有的云端存档与最高分成绩，继续游玩。

**Why this priority**: 这是"切设备了也能用"的完整形态，但依赖 User Story 2 的存档能力
与微信登录的接入（客户端尚未开始接入），且用户已将整体存档功能标注为低优先级。

**Independent Test**: 在设备 1 上以微信身份保存进度，在设备 2 上用同一微信账号登录后
拉取存档，验证进度与最高分归属均迁移成功。

**Acceptance Scenarios**:

1. **Given** 玩家 A 在旧设备上有云端存档与最高分记录，**When** A 在新设备上用同一微信
   账号登录，**Then** 新设备可恢复 A 的存档，且排行榜上的成绩仍归属于 A。
2. **Given** 微信登录失败或身份校验未通过，**When** 尝试恢复，**Then** 恢复被拒绝并
   提示原因，且不泄露任何其他玩家的数据。
3. **Given** 玩家 A 已在新设备上完成迁移，**When** A 在新设备上继续游玩并保存，**Then**
   后续存档与成绩延续同一身份，不产生重复玩家。

### Edge Cases

- 玩家地区信息缺失或无法识别时：该玩家的成绩只参与能确定的层级榜单；三级均无法确定
  时不进入任何地区榜，但个人最高分仍被记录。
- 同一玩家短时间内重复上报同一成绩（如网络重试）：结果与只上报一次完全相同（幂等）。
- 上报的积分为 0、负数或超出合理范围：服务端拒绝并返回明确错误，不污染榜单。
- 玩家修改昵称后：榜单展示该玩家最近一次上报时使用的昵称。
- 两台设备在迁移完成前各自产生了进度：以保存时间最新的一份为准（后写覆盖）。
- 榜单地区中玩家数量少于榜单展示长度：按实际数量展示。
- 存档保存请求在网络中断时失败：客户端可安全重试，服务端保证同一份进度重复保存不产生
  副作用。
- 玩家拒绝或取消微信授权：无法使用云端存档与跨设备恢复，但单机游玩与本设备内体验不受
  影响。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每个玩家持久化其历史最高积分；仅当新上报积分高于历史最高时
  才更新，且更新后旧成绩不再出现在任何榜单。
- **FR-002**: 每条最高分记录 MUST 关联玩家上报时的地区信息（省、市、区三级）与达成时间。
- **FR-003**: 系统 MUST 按省、市、区三个层级分别维护排行榜；榜内按最高积分降序排列，
  积分相同时先达成者在前。
- **FR-004**: 玩家 MUST 能一次性获取自己所在省、市、区三级的榜单，且每个地区层级同时
  提供总榜、月榜、周榜三个时间窗口，每个榜单展示前 100 名的玩家昵称、积分与达成时间。
- **FR-005**: 玩家 MUST 能看到自己在各层级榜单中的当前名次与最高分，即使未进入前 100。
- **FR-006**: 系统 MUST 持久化每个玩家的游戏进度存档（单存档位），保存成功后立即可被
  恢复；新存档覆盖旧存档。
- **FR-007**: 玩家 MUST 能以同一身份在任意时刻取回最近一次保存的存档；无存档时返回明
  确的"无存档"状态。
- **FR-008**: 系统 MUST 支持玩家在新设备上通过微信登录恢复原有身份：同一微信账号在任
  意设备登录后对应同一玩家身份，存档与最高分成绩均归属该身份。
- **FR-009**: 身份凭据校验失败时，系统 MUST 拒绝恢复并且不返回任何其他玩家的存档或个
  人数据。
- **FR-010**: 成绩上报与存档保存 MUST 幂等：同一请求重复到达时结果与到达一次相同。
- **FR-011**: 系统 MUST 校验上报数据的基本合法性（积分为正整数、必要字段齐全），非法
  请求返回明确错误。
- **FR-012**: 系统 MUST 在每个地区层级上维护三个时间窗口的榜单：总榜（全时段历史最高
  分）、月榜（自然月内最高分）、周榜（周一为一周起点的自然周内最高分）；窗口内同样只
  保留每个玩家该窗口内的最高成绩，排序规则与总榜一致（分数降序，同分先达成者在前）。
- **FR-013**: 时间窗口 MUST 自动滚动：进入新的周/月后，对应榜单从零开始重新累计，无需
  任何人工操作；过期窗口的数据由系统自动清理。

### Key Entities *(include if feature involves data)*

- **玩家（Person）**: 游戏用户，具有唯一标识（与其微信身份一一对应）、昵称、创建时
  间、最近登录时间；是成绩与存档的归属主体。
- **地区（Location）**: 玩家所在的省、市、区三级行政区划，随成绩上报提供，用于决定成
  绩进入哪些榜单。
- **最高分记录（Score Record）**: 某玩家的历史最高积分及其达成时间、上报时的昵称与地
  区；每个玩家在同一地区维度下最多一条。
- **排行榜（Leaderboard）**: 某一地区层级（省/市/区中某个具体地区）内所有玩家最高分记
  录的有序集合。
- **游戏存档（Game Save）**: 玩家的游戏进度快照（如当前关卡、金币、对局随机因子等游戏
  内状态）及保存时间；每个玩家一份。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 玩家上报新的最高分后，5 秒内在对应的省、市、区榜单中可见最新成绩。
- **SC-002**: 95% 的榜单查看请求在 1 秒内完整呈现三级榜单内容。
- **SC-003**: 恢复的存档与最后一次成功保存的进度 100% 一致，存档数据零丢失。
- **SC-004**: 完成跨设备迁移的玩家可在 2 分钟内在新设备上继续游玩原进度。
- **SC-005**: 系统支持至少 10,000 名注册玩家与 100 个并发请求而无可感知的性能劣化。
- **SC-006**: 重复或乱序的上报请求不产生任何重复榜单条目或错误成绩（抽查正确率 100%）。

## Assumptions

- 地区信息由客户端随请求提供（来自玩家设置或设备定位），服务端不对其真实性做二次校验。
- 地区维度仅为省、市、区三级，与现有设计一致；全国榜不在本次范围内。
- 排行榜时间窗口为总榜/月榜/周榜三种；周以周一为起点（ISO 周），月为自然月，时间基准
  为 Asia/Shanghai 时区；赛季榜等其它周期不在范围内。
- 周榜/月榜数据仅保存在在线存储中（需求方已确认）：极端数据丢失场景下当期周/月榜清零
  重新累计，总榜可从持久备份完整恢复；建议开启在线存储自身的持久化以进一步降低风险。
- 每级榜单展示长度默认前 100 名。
- 每个玩家仅有一个存档位，采用"后写覆盖"策略解决冲突，无需人工合并。
- 玩家昵称以最近一次上报时提供的为准，服务端不做昵称唯一性约束。
- 跨设备身份识别采用微信登录：微信为每位玩家提供该游戏范围内稳定且唯一的标识，微信是
  本次唯一支持的身份提供方（客户端尚未开始接入微信登录）。
- 微信登录接入完成前，玩家以客户端生成的本地身份游玩；过渡期本地身份与微信身份之间的
  成绩/存档合并不在本次范围内（默认不合并）。
- 客户端为 Cocos 游戏 five_card，由其负责触发保存时机与展示交互；本规格只约束服务端
  对外行为。
- 游戏为单机玩法加轻量社交（排行榜），无实时对战需求，常规互联网延迟可接受。
